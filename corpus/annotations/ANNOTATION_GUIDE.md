# AgentProof Human Annotation Guide

**Version:** 1.0 (frozen before annotation begins; any change after the pilot
bumps the version and is recorded in the change log at the bottom)
**Implements:** `papers/paper1/aaai/TOP_TIER_RESEARCH_PLAN.md`, section 3.3
("Minimum human-validation protocol")
**Samples:** `corpus/annotations/samples_manifest.json`
(generated by `scripts/make_annotation_samples.py`, seed 20260713)
**Worksheets:** `corpus/annotations/worksheet_task1_reconstruction_{A,B}.json`,
`corpus/annotations/worksheet_task2_defects_{A,B}.json`

---

## 0. Who annotates, and what they may not look at

- Two annotators (**A** and **B**) who did **not** create the original LLM
  labels. Prefer annotators with Python experience and at least one agent
  framework (LangGraph, AutoGen, CrewAI, or Google ADK) background. If a paper
  author annotates, the paper must state this, and the author must be blinded
  as described below.
- **Blinding.** Until an annotator has committed (Section 4) their labels for
  a workflow, they must not open, for that workflow:
  - the extracted graph (`corpus/real_world/graphs/<slug>.json`),
  - the LLM ground-truth reconstruction
    (`corpus/real_world/ground_truth/<slug>.json`),
  - any triage or label file (`corpus/real_world/validated_results*.json`,
    `gt_triage_results.json`, `gt_flags_for_triage.json`,
    `revision_analyses.json`),
  - the other annotator's worksheet,
  - the paper's results sections.

  Exception: Task 2 flag items require knowing *which check fired and where*
  (Section 8.2); annotators see the flag's check id and witness detail as
  copied into the manifest, but not the prior triage label.
- **Source of truth** is the pinned source file: fetch
  `https://github.com/<repository>/blob/<commit_sha>/<source_path>` (the
  manifest field `source_url`). Annotate the file at that commit only. If the
  file imports sibling modules of the same repository that define the workflow
  (e.g. sub-agents in another file), you may read those at the same commit and
  must cite them as `path:line`. No local source snapshots are shipped in this
  repository (recorded as a gap in the manifest).

## 1. Labels used everywhere

Every judgment field in both tasks admits the full label set for that field
**plus**:

- `insufficient_evidence` — the source at the pinned commit does not contain
  enough information to decide (e.g. the topology is built from a config file
  not in the repository, the routing function is generated at runtime, or a
  required sibling module is absent). Record *what* is missing in the
  rationale. **Never guess.** An `insufficient_evidence` answer is a valid,
  reportable outcome, not a failure.

In Task 1, `insufficient_evidence` may also be *scoped*: you can reconstruct
the nodes but mark the edge set (or a single edge, node kind, or tool binding)
as unknown, using the `insufficient_evidence_scope` list in the worksheet
(e.g. `["edges", "tools:planner"]`).

---

## 2. The locking rule (read this twice)

> **Disagreements are not discussed, mentioned, hinted at, or resolved until
> BOTH annotators' initial labels are committed.**

Concretely:

1. Each annotator works alone, in their own worksheet file.
2. Committing = setting `"committed": true` on the item **and** making a git
   commit of the worksheet file. The git history is the tamper-evident lock.
3. No communication about any item's content — not even "item 12 is weird" —
   until both worksheets contain committed labels for the item set being
   compared. Process questions ("which file is the entry point?") go to the
   study coordinator, who answers without revealing the other annotator's
   state.
4. All agreement statistics in the paper (Sections 7.3 and 8.4) are computed
   on the committed pre-adjudication labels. Adjudication (Section 9) happens
   strictly afterwards and produces a *separate* adjudicated label set.
5. Labels are never edited after commit. Corrections happen only through
   adjudication, and both versions stay in the record.

---

## 3. Citation and rationale requirements

Every **defect label** (Task 2, both flag items and no-flag items) must carry:

- `source_line_citations`: at least one `path:line` or `path:line-line`
  citation into the pinned source that the label rests on. Cite the lines that
  *create* the relevant structure (the `add_edge` call, the `Task(...)`
  constructor, the `sub_agents=[...]` list), not merely nearby code.
- `rationale`: 1–5 sentences explaining why the cited lines support the label.
  A rationale that could equally support the opposite label is insufficient.

Task 1 reconstructions do not require per-edge citations, but every node and
edge you record should be traceable to source; use the worksheet `notes` field
for anything non-obvious (e.g. "edges 4–6 from the dict returned by
`route_next()` at lines 88–95").

## 5. Operational definitions

These definitions bind both tasks. Each comes with, per framework, one
**worked example** (counts) and one **counterexample** (does not count). The
snippets are miniature but realistic; line references in your own annotations
must point at the real source.

### 5.1 Workflow node

**Definition.** A *workflow node* is a unit of computation that the framework
schedules as a step of the workflow: it can be entered, do work (call an LLM,
call a tool, ask a human, route), and be left. One node per framework-level
step declaration — not per Python function, not per line. Sentinels (5.5,
5.6) are also nodes. Helper functions, prompt templates, plain data objects,
and LLM/client objects are **not** nodes.

Nodes carry a **kind**, one of:
`entry`, `exit`, `tool` (executes a bound non-LLM capability), `llm` (a step
whose work is an LLM call), `router` (its job is choosing the next node),
`human` (blocks on a human), `subgraph` (a nested workflow), `passthrough`
(state shuffling only, no LLM/tool/human). If genuinely undecidable from
source, set `"kind": "insufficient_evidence"`.

| Framework | Worked example (each is ONE node) | Counterexample (NOT a node) |
|---|---|---|
| **LangGraph** | `graph.add_node("summarize", summarize_fn)` → node id `summarize` | `llm = ChatOpenAI(model="gpt-4o")` — a client object, referenced by nodes, is not itself a node |
| **AutoGen** | `writer = AssistantAgent("writer", model_client=mc)` listed in `RoundRobinGroupChat(participants=[writer, critic])` → node id `writer` | `termination = MaxMessageTermination(10)` — a termination condition configures the loop; it is not a schedulable step |
| **CrewAI** | `research_task = Task(description="Research topic X", agent=researcher)` wired into a `Crew(tasks=[research_task, ...])` → one node per `Task` | `researcher = Agent(role="Researcher", ...)` **alone**: in a task-based crew the schedulable steps are the Tasks; an Agent never placed on a task/crew is not a node |
| **ADK** | `verifier = LlmAgent(name="verifier", model="gemini-2.0-flash", ...)` appearing in some agent tree → node id `verifier` | `SequentialAgent(name="pipeline", sub_agents=[a, b])` contributes a *container*; its ordering becomes edges between `a` and `b` — reconstruct the container as a `subgraph` node only if it does work of its own, otherwise record its children and edges |

Node **id convention** (needed for F1 matching, Section 7.3): use the
framework-declared name — LangGraph `add_node` string; AutoGen agent `name`;
ADK agent `name`; CrewAI task variable name or `Task(name=...)`, else the
first ~50 chars of the description, lowercased, spaces→`_` (this matches the
project's extractor convention). Sentinels are always `__start__` / `__end__`.

### 5.2 Control edge

**Definition.** A *control edge* `u → v` exists when, per the framework's
execution semantics at the pinned commit, node `v` can execute immediately
after node `u` in some run. Edges carry a kind: `direct` (unconditional),
`conditional` (guarded by a router/condition), `parallel` (fan-out executed
concurrently), `loop` (back-edge of an iteration construct). Edges the
framework implies (AutoGen round-robin order, CrewAI sequential task order,
ADK `SequentialAgent` ordering) **count as real edges** — record them; the
whole point of Task 1 is to compare human recovery of implicit topology
against the extractor's.

| Framework | Worked example | Counterexample |
|---|---|---|
| **LangGraph** | `graph.add_edge("retrieve", "grade")` → `retrieve → grade` (direct); `graph.add_conditional_edges("grade", decide, {"good": "answer", "bad": "rewrite"})` → two `conditional` edges | `state["next"] = "answer"` inside a node body — writing state is not an edge unless a conditional-edge function dispatches on it (then the edge belongs to the dispatch declaration) |
| **AutoGen** | `RoundRobinGroupChat([a, b, c])` → cycle `a → b → c → a` (direct/loop); `SelectorGroupChat([a, b, c])` → all ordered pairs among participants (conditional), selector permitting | `a.send(b, "seed message")` in a driver script before the chat starts — one-off setup message, not part of the recurring team topology |
| **CrewAI** | `Crew(tasks=[t1, t2], process=Process.sequential)` → `t1 → t2` (direct, implied by list order) | `t2 = Task(..., context=[t1])` — `context` alone is a **data** dependency (5.3); the control edge exists here only because of the sequential process order |
| **ADK** | `SequentialAgent(sub_agents=[fetch, clean, report])` → `fetch → clean → report`; `ParallelAgent(sub_agents=[x, y])` → `parallel` fan-out to `x` and `y` | `report = LlmAgent(..., tools=[AgentTool(agent=clean)])` — invoking another agent *as a tool* is a tool binding on `report` (5.4), not a control edge, unless it demonstrably transfers control of the workflow |

### 5.3 Data dependency

**Definition.** A *data dependency* `u ⇒ v` exists when output produced by `u`
is consumed by `v` (shared state key written by `u` and read by `v`, task
output passed as context, message content consumed downstream). Data
dependencies are recorded in Task 1 `notes` when they explain your decisions
(they are **not** scored as edges); they matter for judging defects ("dead
end" is worse when downstream nodes need its output).

| Framework | Worked example | Counterexample |
|---|---|---|
| **LangGraph** | node `retrieve` returns `{"docs": ...}`; node `answer` reads `state["docs"]` → `retrieve ⇒ answer` | both nodes read the *input* key `state["question"]` — shared read of an input is not a dependency between them |
| **AutoGen** | `critic`'s reply is consumed by `writer`'s next turn in the same chat → `critic ⇒ writer` | two agents each having the same system prompt text — configuration similarity is not data flow |
| **CrewAI** | `t2 = Task(..., context=[t1])` → `t1 ⇒ t2` | `t1` and `t2` sharing the same `Agent` — executor sharing is not data flow |
| **ADK** | `LlmAgent(..., output_key="draft")` then a later agent's instruction reads `{draft}` → dependency | two agents using the same `model="gemini-2.0-flash"` string |

### 5.4 Tool binding

**Definition.** A tool is *bound* to a node when the framework declaration
gives that node the capability to invoke it: it appears in the node's
`tools=[...]` (or equivalent) at the pinned commit. Record the declared tool
names (function name or tool object name). A node whose *body* calls a
library function without a framework-level declaration is a **body call** —
record it in Task 1 as a binding with `"declared": false` (this is exactly
the extractor's known blind spot, so we measure it), and note the call line.

| Framework | Worked example | Counterexample |
|---|---|---|
| **LangGraph** | `graph.add_node("tools", ToolNode([search, calculator]))` → node `tools` binds `search`, `calculator`; also `llm.bind_tools([search])` used by node `agent` | a docstring or prompt that merely *mentions* "you can search the web" with no tool object |
| **AutoGen** | `AssistantAgent("coder", tools=[run_pytest])` → binds `run_pytest`; v0.2 `register_function(f, caller=coder, executor=proxy)` | `code_execution_config={"work_dir": ...}` on its own configures an executor; record it as binding `code_execution` only if a code block can actually reach it in this script |
| **CrewAI** | `Agent(role="analyst", tools=[SerperDevTool()])` executing task `t1` → `t1` binds `SerperDevTool` | `tools=[]` (empty list) — an *empty* declaration is not a binding; a `tool`-kind node with no bindings is exactly what the `tool_declarations` check flags |
| **ADK** | `LlmAgent(name="db", tools=[execute_sql])` → binds `execute_sql` | `instruction="use the execute_sql tool"` with no `tools=` argument — prompt text is not a binding (but note it; it is evidence for intent in Task 2) |

### 5.5 Entry

**Definition.** The *entry* is the unique sentinel node `__start__` from which
execution begins. Record which real node(s) `__start__` connects to: the
node(s) the framework executes first.

| Framework | Worked example | Counterexample |
|---|---|---|
| **LangGraph** | `graph.add_edge(START, "ingest")` or `graph.set_entry_point("ingest")` → `__start__ → ingest` | the first `add_node` call in the file — declaration order does not determine the entry |
| **AutoGen** | the initiating message `user_proxy.initiate_chat(manager, ...)` or `team.run(task=...)` → `__start__ →` first speaker | the first agent constructed in the file |
| **CrewAI** | first task in `Crew(tasks=[t1, ...])` (sequential) → `__start__ → t1`; hierarchical: `__start__ →` manager | the first `Agent(...)` defined |
| **ADK** | the root agent passed to the `Runner` / exported as `root_agent` → `__start__ →` root | any sub-agent constructed earlier in the file |

If the entry cannot be determined (library file with no composition), mark
`entry_id: "insufficient_evidence"`.

### 5.6 Exit

**Definition.** An *exit* is the sentinel `__end__`, reached when the workflow
terminates normally. Record an edge `u → __end__` for every node `u` after
which the framework stops the run: explicit `END`/finish edges, the last task
of a sequential process, satisfaction of a termination condition attached to
the loop, or the root agent completing.

| Framework | Worked example | Counterexample |
|---|---|---|
| **LangGraph** | `graph.add_edge("answer", END)`; `add_conditional_edges("router", f, {..., "done": END})` → `answer → __end__`, `router → __end__` | a node function that `return`s state — every node returns; returning is not terminating |
| **AutoGen** | `RoundRobinGroupChat(..., termination_condition=TextMentionTermination("DONE"))` → each participant that can utter DONE gets an edge to `__end__` | `max_consecutive_auto_reply=5` on one agent silences that agent; whether it ends the *chat* depends on the pattern — if unclear, mark the exit-edge set `insufficient_evidence` rather than inventing edges |
| **CrewAI** | last task of `Process.sequential` → `t_last → __end__` | `verbose=True` output ending in the console |
| **ADK** | root `SequentialAgent` finishing its last child → `last_child → __end__` | a `LoopAgent` without `max_iterations` or an escalation tool has **no** implicit exit from the loop — do not add one (that absence is signal, not noise) |

### 5.7 Deliberate wait state

**Definition.** A *deliberate wait state* is a node with no outgoing edge (or
no path to `__end__`) **by design**: the run intentionally halts there and an
*outer driver* (a REPL loop, web handler, or re-invocation with accumulated
state) resumes the workflow. This is the single most common reason a true
dead end is *not* a defect, so evidence must be explicit: a docstring/comment
stating the wait, an outer loop that re-invokes, or a framework interrupt
mechanism.

| Framework | Worked example | Counterexample |
|---|---|---|
| **LangGraph** | `wait_for_user` node with no out-edges + outer `while True: graph.invoke(state)` appending the user's reply each turn; or `interrupt()` / `interrupt_before=["approve"]` with a checkpointer | a `draft_response` node the author simply forgot to wire to `send` — no outer driver, no comment, downstream nodes exist that consume its output: that is a dead-end defect |
| **AutoGen** | `UserProxyAgent(human_input_mode="ALWAYS")` — the chat blocks for a human every turn by design | a group chat whose termination condition can never fire (e.g. `TextMentionTermination("APPROVED")` but no agent is instructed to say APPROVED) — that is a livelock, not a wait |
| **CrewAI** | `Task(..., human_input=True)` — the task pauses for human review before completing | a task whose output feeds nothing and is never returned — unused terminal work, judge under 5.9 |
| **ADK** | a long-running/`get_user_choice`-style tool that ADK pauses on | `LoopAgent` with no exit path and no human tool — livelock candidate |

### 5.8 Human gate

**Definition.** A *human gate* is a `human`-kind node (or an in-node human
approval mechanism: `interrupt()`, `human_input=True`,
`human_input_mode="ALWAYS"`, an ADK human/confirmation tool) positioned so
that **every path** from `__start__` to a given sensitive action passes
through it before the action executes. A human node that is reachable but
*bypassable* (some path reaches the sensitive tool without it) is not a gate
for that tool — that is exactly what the `human_gate_coverage` check tests
(BFS from entry with human nodes removed; see
`src/agentproof/verify/structural.py`, check 5b).

*Sensitive* tools, per the paper's lexicon (`scripts/risk_aware_gate.py
SENSITIVE_KEYWORDS`): destructive (delete/drop/kill/...), write
(insert/update/save/...), exec (execute/shell/deploy/...), communications
(send/email/publish/...), financial (payment/transfer/refund/...). Use the
lexicon as a starting point but judge the *actual effect* from source.

| Framework | Worked example (gate) | Counterexample (not a gate) |
|---|---|---|
| **LangGraph** | `add_node("approve", human_approval)` with `interrupt_before=["approve"]`, and the only edge into `send_email` comes from `approve` | an `approve` node exists, but `add_conditional_edges("triage", f, {"urgent": "send_email", ...})` routes urgent mail straight to `send_email` — bypassable, hence ungated |
| **AutoGen** | `UserProxyAgent(human_input_mode="ALWAYS")` is the executor for the `transfer_funds` function | `human_input_mode="NEVER"` proxy that auto-executes tool calls; or the human agent participates in chat but the tool executes on a different agent's turn regardless |
| **CrewAI** | `Task(description="review and approve the post", human_input=True)` ordered *before* the publishing task in a sequential crew | `human_input=True` on the *last* task while the `publish` tool is bound to an *earlier* task — the gate comes after the action |
| **ADK** | a `confirm_with_user` tool that the instruction requires before `execute_transfer`, enforced by a sequential sub-agent ordering `confirm → transfer` | instruction text saying "DO NOT ask for confirmation" (a real observed anti-gate), or a parallel branch that reaches the payment agent without the confirm agent |

### 5.9 Genuine defect

**Definition.** A flag denotes a *genuine defect* when ALL of the following
hold on the **faithful** topology (the one you would reconstruct from
source, not the possibly-wrong extracted/reconstructed graph):

1. **Faithful:** the flagged structure really exists in the source-level
   behavior (it is not an artifact of a wrong graph);
2. **Unintended:** it is not a deliberate wait state (5.7), documented design
   choice, or inherent framework convention (e.g. AutoGen chat loops have no
   static exit — that alone is not a defect);
3. **Consequential:** in some plausible execution it causes concrete harm —
   silent halt losing user work, an unreachable advertised behavior, an
   unreviewed side effect (email actually sent, SQL actually executed, money
   actually moved), or a control-flow wiring that contradicts the code's own
   stated intent.

If 1–2 hold but consequence is debatable, use `arguable`, not
`genuine_defect`. If you cannot establish faithfulness from source, use
`insufficient_evidence`.

Per-framework worked example / counterexample:

| Framework | Genuine defect (example) | Not a defect (counterexample) |
|---|---|---|
| **LangGraph** | a chatbot whose SQL-executing tool node is reachable from `__start__` with no human gate on any path, in an app that runs user-supplied questions against a live DB | `wait_for_user` dead end with an outer re-invoke loop (deliberate wait state, 5.7) |
| **AutoGen** | a payments pipeline whose agent instructions say "DO NOT confirm, IMMEDIATELY PROCEED" while `transfer` executes real transactions — missing human gate with live side effects | a brainstorm group chat with no human agent and no side-effecting tools — `human_presence` fires, but nothing needs gating (intentional) |
| **CrewAI** | a 2-task crew whose agents carry Gmail/Calendar MCP tools and neither task sets `human_input=True`, with the result discarded (agents act during kickoff, nobody reviews) | final task output not connected to anything downstream in a demo whose README says "prints the report" — by-design terminal output |
| **ADK** | a router/dispatcher whose transfer targets don't match the declared sub-agents (mis-wiring: an advertised branch can never run) | `SequentialAgent` last child having no explicit out-edge — the framework supplies termination; the "missing" edge is a graph-model convention, not a source defect |

#### Defect taxonomy (what each check claims; see `src/agentproof/verify/structural.py`)

| check id | category | fires when | typical genuine case | typical non-genuine case |
|---|---|---|---|---|
| `exit_reachability` | structural | some declared exit is unreachable from entry | advertised "done" path can never run | extractor synthesized/missed edges (artifact) |
| `reverse_reachability` | structural | a reachable node has no path to any exit (livelock) | run enters a subgraph it can never leave, losing work | deliberate wait state (5.7); chat-loop convention |
| `dead_ends` | structural | a non-exit node has no successor | forgot to wire `draft → send`; downstream consumers exist | deliberate wait state; framework-implied termination |
| `router_shape` | structural | a `router` node has non-`conditional` out-edges | router wired to targets that bypass its own decision, or targets that don't exist | node mis-kinded as router by the graph, or convention mismatch |
| `tool_declarations` | structural | a `tool`-kind node declares no tools | capability genuinely missing so the step can't do its job | node calls tools in its body without framework declaration (kind/binding error in the graph) |
| `human_presence` | policy (blunt) | no `human` node anywhere | side-effecting workflow that needed review | any low-stakes workflow (most firings are intentional) |
| `human_gate_coverage` | policy (risk-aware) | a sensitive tool is reachable with all human nodes removed | ungated SQL-exec / payment / email path | tool name matches lexicon but has no real side effect (e.g. `save_to_memory`) |

## 6. Label vocabularies

### 6.1 Task 2 flag items (`label` field)

- `genuine_defect` — meets all three criteria of 5.9.
- `intentional` — structure is real but deliberate (wait state, design
  choice, framework convention, or the workflow legitimately needs no human).
- `model_error` — the flag exists only because the graph it was computed on
  (extracted or reconstructed) misrepresents the source. Name the
  misrepresentation in the rationale.
- `arguable` — faithful and unintended-looking, but consequence or intent is
  genuinely debatable after full review.
- `insufficient_evidence` — cannot decide from the pinned source.

### 6.2 Task 2 no-flag items (`verdict` field)

- `has_genuine_defect` — you found a defect (5.9) that raised **no** flag;
  set `defect_check_id` to the closest taxonomy row (or `other`), and cite
  lines.
- `no_defect` — reviewed, none found.
- `insufficient_evidence`.

### 6.3 Task 1 node kinds

`entry | exit | tool | llm | router | human | subgraph | passthrough |
insufficient_evidence` (definitions in 5.1).

## 7. Task 1 protocol — graph reconstruction

**Sample:** the 32 workflows in `reconstruction_sample` (8 per framework,
4 application-like + 4 tutorial/demo/test each), pilot items first.

**Procedure (per workflow, per annotator, independently):**

1. Fetch the pinned source (`source_url`). Read the whole file; follow
   same-repo imports if they define workflow structure.
2. Record in the worksheet: `entry_id`, `exit_ids`, `nodes` (id, kind, tools
   with `declared: true|false`), `edges` (source, target, kind). Follow the
   id conventions in 5.1 (sentinels `__start__`/`__end__`).
3. Use `insufficient_evidence` / `insufficient_evidence_scope` per Section 1.
4. Set `committed: true`, git-commit the worksheet.

**Scoring (computed by the coordinator after both annotators commit; the
formulas are fixed here so they cannot be chosen post hoc):**

- **Pairwise node F1** between A and B: match nodes by canonicalized id
  (lowercase, trim, sentinel aliases `__entry__`≡`__start__`,
  `__exit__`≡`__end__`). F1 = 2·|A∩B| / (|A|+|B|).
- **Pairwise edge F1**: edges as ordered pairs of canonicalized ids, matched
  exactly; same F1 formula. Report edge F1 both over all edges and excluding
  sentinel-incident edges (sensitivity).
- **Kind agreement**: over matched nodes, raw percent agreement and Cohen's
  kappa over the 8-kind vocabulary (+`insufficient_evidence` as its own
  category).
- All three reported overall and per framework, with workflow-level
  repository-clustered bootstrap 95% CIs (10,000 resamples), **before any
  adjudication**.
- **Adjudication** (Section 9) then produces one adjudicated human graph per
  workflow.
- **Adjudicated extractor precision/recall**: score the AST-extracted graph
  (`corpus/real_world/graphs/<slug>.json`) against the adjudicated human
  graphs — node P/R, edge P/R, kind accuracy — with the same matching rules,
  mirroring `scripts/extractor_accuracy.py`. Secondarily, score the LLM
  ground-truth graphs (`corpus/real_world/ground_truth/<slug>.json`) against
  the adjudicated human graphs, which directly measures the quality of the
  labels the paper currently relies on.

## 8. Task 2 protocol — defect labeling

**Sample** (all in the manifest):

- **8.1 (context)** Each item names a workflow, a `check_id`, and (for GT
  flags) the flag's witness detail.
- **8.2 flag items** (`defect_label_sample`, 18 items): every flag raised on
  the reconstructed ground-truth graphs (16), plus the two extracted-graph
  flags claimed genuine by the paper's triage — so all four claimed genuine
  defects are independently re-reviewed. You see the check id and witness,
  never the prior label.
- **8.3 no-flag items** (`no_flag_sample`, 32 workflows): repository-
  stratified random workflows on which the instrument raised no
  structural/gate flag. Task: an open false-negative audit — read the source
  and decide whether any taxonomy defect (Section 5.9 table) is present.

**Procedure (per item, per annotator, independently):** fetch pinned source →
verify the flagged structure exists in source (faithfulness) → judge intent
(5.7, docstrings, drivers, READMEs at the same commit) → judge consequence
(what actually executes; side effects real or mocked?) → assign the label
(6.1/6.2) with citations and rationale (Section 3) → commit.

**8.4 Scoring (fixed in advance, computed pre-adjudication):**

- Raw percent agreement, per item class (flag items; no-flag items) and
  pooled.
- Chance-corrected agreement: **Krippendorff's alpha** (nominal) as primary
  — it handles the `insufficient_evidence` category and any missing labels —
  with **Cohen's kappa** as a secondary check. Uncertainty: nonparametric
  bootstrap over items, 10,000 resamples, 95% percentile CI; for the pooled
  statistic, resample repositories (clusters), not items.
- Report the confusion matrix between annotators over the full label set.
- Report agreement **before adjudication** always; adjudicated labels are an
  additional, separately-labeled column, never a replacement.
- The paper's prevalence re-estimate uses adjudicated labels; a sensitivity
  row uses only items where A and B independently agreed.
- **Do not** present agreement on the flag items (a selected set) as
  validation of prevalence; prevalence claims rest on the no-flag audit plus
  the flag items together (plan 3.3).

---

## 9. Adjudication (only after locks)

1. Coordinator verifies both worksheets are committed for the item set
   (git history is the evidence).
2. A and B meet; for each disagreement, each states their rationale; they may
   re-read source together.
3. Consensus label → adjudicated set, with a note
   `adjudication: "A→B" | "B→A" | "both→new" | "unresolved"`.
4. `unresolved` items keep both labels and are reported as `arguable` /
   excluded per the paper's stated rule — never silently dropped.
5. Adjudicated files live next to the worksheets as
   `adjudicated_task1.json` / `adjudicated_task2.json`; initial worksheets
   are never modified.
